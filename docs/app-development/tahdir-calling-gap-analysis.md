# تحليل الفجوات: ميزة النداء في تحضير (v5website + v5app) مقابل okta-calling

> **المصدر**: قراءة مباشرة لميزة النداء في `TahdirIT/v5website` عند `e344054`
> (‏~1500 سطر PHP متعلقة بالنداء والانصراف) و `TahdirIT/v5app` عند `af255e8`
> (‏~1300 سطر Dart)، ومقارنتها بحال `getokta/okta-calling` عند `d42420f` —
> وهو اليوم **هيكل مولَّد فارغ**: صفحة dashboard واحدة، تطبيق مصغّر قالبي
> (81 سطراً)، لا نماذج ولا migrations وظيفية. كل بند أدناه مذكور معه موضعه
> في كود تحضير للرجوع إليه عند التنفيذ.
>
> **ما ليس فجوة**: العزل عبر Partner API، جمهور وليّ الأمر المحروس
> (`EnsureAppAudience`)، النشر source-on-device — هذه يملكها okta ولا يملكها
> تحضير. التحليل باتجاه واحد عمداً: ماذا ينقصنا نحن.
>
> **شقيق هذا الملف**: [`tahdir-gap-analysis.md`](./tahdir-gap-analysis.md)
> (الحضور مقابل okta-hdor). قرار المالك القائم: الأعذار تطبيق مستقل،
> والنداء تطبيق مستقل (`okta-calling`) — هذا الملف يخص الأخير.

## 1. خلاصة تنفيذية

النداء في تحضير **رحلة انصراف جغرافية** كاملة الحلقة: وليّ الأمر (أو مفوَّض
عنه) يعلن «في الطريق» ثم «واصل» — والوصول محكوم بسياج جغرافي حول المدرسة —
ثم «استلمت»، وكل مرحلة تُختم بوقت وموقع. المدرسة تراقب شاشة حيّة تتحدّث
كل 5 ثوانٍ وتُصدر صوتاً عند كل قادم جديد، وتُقفل اليوم بتسجيل «انصراف»
يُطلق إشعاراً لوليّ الأمر (تطبيق/واتساب/SMS).

okta-calling اليوم صفر وظيفي. لكن الفجوة الحقيقية ليست «انسخ الشاشات» —
ثلاثة من أعمدة النداء في تحضير تقف على **قاعدة بيانات مشتركة** لا تملكها
تطبيقات okta المعزولة، وواحد يقف على **قدرات جهاز** لا يمنحها عقد المضيف
الحالي:

1. **ساعة المدرسة** (وقت الانصراف → نافذة النداء): تحضير يقرأها من `shifts`
   المشترك؛ عندنا تعيش نسخة منها داخل okta-hdor **في schema معزول** لا
   يصله okta-calling.
2. **شرط الحضور** (لا نداء لغائب أو منصرف): تحضير يقرأ `attendances` مباشرة؛
   عندنا سجل الحضور بيانات تطبيق okta-hdor — لا مسار بين التطبيقين اليوم.
3. **آخر حصة في الجدول** (انصراف يعتمد على الجدول الدراسي): تحضير يقرأ
   `scheduleds`؛ عندنا الجدول بيانات okta-smart-timetable.
4. **الموقع الدقيق**: تحضير يشترط دقة ≤ 30م ويرفض ما دونها؛ عقد `okta_host`
   الخامس يعطي **إحداثية خشنة واحدة** بلا ضمان دقة.

القرار المعماري المطلوب قبل أول سطر كود في القسم 5.

## 2. جرد ميزة النداء في تحضير

### 2.1 نموذج البيانات (v5website)

| الجدول | الحقول الجوهرية | الموضع |
|---|---|---|
| `calls` | school/term/shift/student + **morph caller** (وليّ أمر أو مفوَّض) + `date` + ثلاث مراحل موقوتة كلٌّ بموقعها: `on_way_time`+FK، `arrived_time`+FK، `pickup_time`+FK + soft deletes | `2024_07_01_100411_create_calls_table` |
| `dismissals` | school/term/shift + **morph dismissable** (طالب أو موظف) + `status` (dismissed/excused) + date/time + note + **morph causer** + unique(dismissable, date, shift, term) | `2024_06_30_074700_create_dismissals_table` |
| `locations` | lat/lng — صف لكل حدث عبر `firstOrCreate` | `0001_..._create_locations_table` |
| `representatives` | student + user + **roles** (مجموعة أدوار) + status + `start_at`/`end_at` — المفوَّضون بالاستلام، بصلاحية مؤقتة | `2024_08_06_111719_create_representatives_table` |

الملاحظة البنيوية: **النداء سجلّ واحد لليوم يتقدّم عبر المراحل**
(`updateOrCreate` يملأ العمود التالي)، لا ثلاثة أحداث منفصلة. الحالة تُشتق
من أيّ الأعمدة مملوء (`pickup ⊃ arrived ⊃ on_way`) — في الخادم
(`CallService::studentCall`) وفي التطبيق (`_fromCallRecord`) بنفس المنطق.

## 5. الفجوات البنيوية — ما يحتاج **قراراً** قبل التنفيذ

هذا جوهر الملف. تحضير monolith: النداء والحضور والجدول والورديات في schema
واحد فيقرأ بعضها بعضاً مجاناً. تطبيقات okta معزولة عمداً — schema لكل
تثبيت، و`BlocksPartnerDirectAccess` على نماذج المنصة. أربع قدرات تصطدم
بهذا العزل أو بحدود عقد المضيف:

### 5.1 ساعة المدرسة (وقت الانصراف)

- **تحضير**: `shift.dismiss_time` من الـ schema المشترك.
- **عندنا**: النظير (`checkout_from`/`checkout_until` في `okta_hdor_work_times`)
  معزول داخل okta-hdor.
- **الخيار أ — المطروح لـ v1**: okta-calling يملك إعداداته الزمنية الخاصة
  (صفحة «وقت الانصراف + مدة ما قبل النداء» لكل مدرسة × يوم، بنمط work-times
  في hdor). تكرار إدخال مقبول مقابل صفر اعتماد متبادل.
- **الخيار ب — منصّي لاحقاً**: «ساعة المدرسة» بيانات منصّة بـ scope
  (`education.schedule.read`) يستهلكه hdor و calling وكل قادم. الأصحّ
  استراتيجياً، لكنه موجة منصّة (okta-web + seeder + catalog) لا موجة تطبيق.

### 5.2 شرط الحضور وعدم الانصراف قبل النداء

- **تحضير**: يقرأ `attendances` و`dismissals` مباشرة.
- **عندنا**: سجل الحضور بيانات okta-hdor؛ لا مسار قراءة بين تطبيقين اليوم.
  السابقة الوحيدة للتخاطب بين التطبيقات هي حدث المدفوعات in-process
  (`ChargeUpdated`) — مخصوص بالمدفوعات، غير معمَّم.
- **المطروح لـ v1**: إسقاط الشرط — النداء يعمل مستقلاً (نداء لغائب حالة
  هامشية يلحظها المشغّل بصرياً).
- **لاحقاً**: تعميم نمط الأحداث (`AttendanceUpdated` من hdor يستمع له
  calling in-process) — موجة منصّة، وتفتح الباب لكل تكامل قادم
  (النداء يُقفل تلقائياً بعد تسجيل الانصراف مثلاً).

### 5.3 الموقع الدقيق (فجوة **عقد مضيف**)

- **تحضير**: `LocationAccuracy.high` + رفض دقة > 30م + popup لإعدادات النظام.
- **عندنا**: `Okta.location()` إحداثية خشنة واحدة بلا ضمان دقة — كافية
  لـ«قرب المدرسة تقريباً»، غير كافية لسياج بنصف قطر عشرات الأمتار.
- **المطلوب**: عقد 6 يضيف `Okta.preciseLocation()` (طلب دقة عالية + إرجاع
  الدقة الفعلية ليحكم التطبيق بنفسه) — مع إبقاء فلسفة العقد: لا ترمي،
  الرفض نتيجة عادية، وفشل الدقة يُعاد بقيمة سالبة.
- **بوابة القدرة إلزامية**: الدرس المدفوع الثمن في hdor — كل نداء عقد أعلى
  خلف فحص `Okta.contract()`، وإلا انهار المفسِّر على المضيفات الأقدم.

### 5.4 الأصوات المميِّزة (فجوة عقد أصغر)

`playSound` مفرداته ثلاث. شاشة تحضير تميّز سمعياً بين «في الطريق» (بوق)
و«واصل» (جرس). إمّا توسيع المفردات في عقد 6 (`chime`/`horn` — تبقى مفردات
مغلقة، لا مسارات ملفات)، أو القبول بـ `success`/`warning` للتمييز في v1.

### 5.5 «الحيّة» في التطبيق المصغّر

قيد صريح لا يملكه تحضير: **لا `Timer` في مفسِّر التطبيقات المصغّرة**، ولا
استئناف async مؤجَّل آمن (انهيار اليوم شاهد). فشاشة تتحدّث كل 5 ثوانٍ
**غير قابلة للبناء داخل التطبيق المصغّر** بالعقد الحالي:

- الشاشة الحيّة للمدرسة ← صفحة Livewire في okta-web (§4.7) حيث الـ polling
  طبيعي.
- سطح التطبيق المصغّر (وليّ الأمر والمشغّل الجوّال) ← تحديث بالأحداث:
  عند الفتح، بعد كل فعل، وزر تحديث — نفس فلسفة drain في hdor.
- إن أردنا حيّاً على الجوال لاحقاً: `Okta.schedule(ms)` (callback دوري
  يديره **المضيف** وينزل للتطبيق كحدث) مرشّح لعقد قادم — يحلّها لكل
  التطبيقات بلا فتح باب الـ async المؤجَّل داخل المفسِّر.

## 7. الترتيب المقترح (موجات okta-calling)

| الموجة | المحتوى | يعتمد على |
|---|---|---|
| **C1** | الأساس: جدول calls + مراحله + مصفوفة التحقق + إعدادات ساعة المدرسة الخاصة (§5.1 خيار أ) + صفحة وليّ الأمر (جمهور guardian) بنافذة النداء والتدرّج | لا شيء خارجي |
| **C2** | السياج الجغرافي بالإحداثية الخشنة المتاحة (نصف قطر متسامح) + شاشة المدرسة الحيّة في okta-web + نداء بالنيابة | C1 |
| **C3** | المفوَّضون (إدارة وليّ الأمر + استلام المفوَّض) | C1 |
| **C4** | كشف الانصراف + قفل التوقيت + إشعار `SendNotification` | C1 |
| **C5** | التطبيق المصغّر: بطاقة الأبناء + أزرار التدرّج + تحديث بالأحداث | C1، بوابة عقد |
| **عقد 6** (منصّة) | `preciseLocation` (§5.3) + مفردات صوت (§5.4) ± `schedule` (§5.5) | مستقلة عن C1–C5 |
| **منصّة لاحقاً** | ساعة مدرسة منصّية (§5.1 ب) + تعميم أحداث بين التطبيقات (§5.2) | قرار منصّة |

القاعدة الناظمة: **C1–C5 لا تنتظر أي تغيير منصّة**. كل ما يحتاج okta-web
أو عقد مضيف جديداً معزول في سطرَي الجدول الأخيرين، يتقدّم بالتوازي ولا
يحجب التطبيق.
